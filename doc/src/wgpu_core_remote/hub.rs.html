1/*! Allocating resource ids, and tracking the resources they refer to.
2
3The `wgpu_core` API uses identifiers of type [`Id<R>`] to refer to
4resources of type `R`. For example, [`id::DeviceId`] is an alias for
5`Id<markers::Device>`, and [`id::BufferId`] is an alias for
6`Id<markers::Buffer>`. `Id` implements `Copy`, `Hash`, `Eq`, `Ord`, and
7of course `Debug`.
8
9[`id::DeviceId`]: crate::id::DeviceId
10[`id::BufferId`]: crate::id::BufferId
11
12[`Id`]s also incorporate a generation number, for additional validation.
13
14The resources to which identifiers refer are freed explicitly.
15Attempting to use an identifier for a resource that has been freed
16elicits an panic.
17
18## Assigning ids to resources
19
20Firefox and Servo allocate ids themselves in the content process using [`IdentityHub`],
21then pass then via IPC to GPU process where it's passed down to
22`Global::device_create_buffer` and friends the id to assign the new
23resource.
24
25Methods that create resources all expect an `id_in` argument
26that the caller uses to specify the id. For example, the
27declaration of `Global::device_create_buffer` looks like this:
28
29```ignore
30impl Global {
31    /* ... */
32    pub fn device_create_buffer(
33        &self,
34        device_id: id::DeviceId,
35        desc: &BufferDescriptor,
36        id_in: id::BufferId,
37    ) {
38        /* ... */
39    }
40    /* ... */
41}
42```
43
44## Id allocation and streaming
45
46Allowing users to assign resource ids themselves
47enables major performance improvements in some applications.
48
49This is designed for use by Firefox's and Servo's [WebGPU] implementation.
50For security, web content and GPU use must be kept
51segregated in separate processes, with all interaction between them
52mediated by an inter-process communication protocol. As web content uses
53the WebGPU API, the content process sends messages to the GPU process,
54which interacts with the platform's GPU APIs on content's behalf,
55occasionally sending results back.
56
57In a classic Rust API, a resource allocation function takes parameters
58describing the resource to create, and if creation succeeds, it returns
59the resource id in a `Result::Ok` value. However, this design is a poor
60fit for the split-process design described above: content must wait for
61the reply to its buffer-creation message (say) before it can know which
62id it can use in the next message that uses that buffer. On a common
63usage pattern, the classic Rust design imposes the latency of a full
64cross-process round trip.
65
66We can avoid incurring these round-trip latencies simply by letting the
67content process assign resource ids itself. With this approach, content
68can choose an id for the new buffer, send a message to create the
69buffer, and then immediately send the next message operating on that
70buffer, since it already knows its id. Allowing content and GPU process
71activity to be pipelined greatly improves throughput.
72
73To help propagate errors correctly in this style of usage, when resource
74creation fails, the id supplied for that resource is marked to indicate
75as much, allowing subsequent operations using that id to be properly
76flagged as errors as well. This is called [Contagious Invalidity].
77
78[`Id<R>`]: crate::id::Id
79[`Id`]: crate::id::Id
80[WebGPU]: https://www.w3.org/TR/webgpu/
81[`IdentityHub`]: wgpu_core_remote_types::identity::IdentityHub
82[Contagious Invalidity]: https://www.w3.org/TR/webgpu/#invalidity
83
84*/

101/// All the resources tracked by a [`crate::global::Global`].
102///
103/// Each field in [`Hub`] is a [`Registry`] holding all the values of a
104/// particular type of resource.
105///
106/// Most `wgpu` operations require access to several different
107/// kinds of resource, so to obtain mutable references
108/// to different fields of your [`Hub`] simultaneously, use
109/// destructing:
110/// ```ignore
111/// fn f(hub: &mut Hub) {
112///     let Hub {
113///         command_encoders,
114///         command_buffers,
115///         ..
116///     } = hub;
117/// }
118/// ```
119pub struct Hub {
120    pub(crate) adapters: Registry<Arc<Adapter>>,
121    pub(crate) devices: Registry<Arc<Device>>,
122    pub(crate) queues: Registry<Arc<Queue>>,
123    pub(crate) pipeline_layouts: Registry<Arc<PipelineLayout>>,
124    pub(crate) shader_modules: Registry<Arc<ShaderModule>>,
125    pub(crate) bind_group_layouts: Registry<Arc<BindGroupLayout>>,
126    pub(crate) bind_groups: Registry<Arc<BindGroup>>,
127    pub(crate) command_encoders: Registry<Arc<CommandEncoder>>,
128    pub(crate) command_buffers: Registry<Arc<CommandBuffer>>,
129    pub(crate) render_bundles: Registry<Arc<RenderBundle>>,
130    pub(crate) render_pipelines: Registry<Arc<RenderPipeline>>,
131    pub(crate) compute_pipelines: Registry<Arc<ComputePipeline>>,
132    pub(crate) pipeline_caches: Registry<Arc<PipelineCache>>,
133    pub(crate) query_sets: Registry<Arc<QuerySet>>,
134    pub(crate) buffers: Registry<Arc<Buffer>>,
135    pub(crate) textures: Registry<Arc<Texture>>,
136    pub(crate) texture_views: Registry<Arc<TextureView>>,
137    pub(crate) external_textures: Registry<Arc<ExternalTexture>>,
138    pub(crate) samplers: Registry<Arc<Sampler>>,
139    pub(crate) render_passes: Registry<RenderPass>,
140    pub(crate) compute_passes: Registry<ComputePass>,
141    pub(crate) render_bundle_encoders: Registry<RenderBundleEncoder>,
142}
